## SCENARIO 3 — что и как проверять

**Цель:** занять глобальный Gradle-lock вторым процессом → агентская сборка ловит `Timeout waiting to lock <cache>... Owner PID: X` → агент выполняет `ps -o pid,stat,args -p X`, отдаёт **INFRASTRUCTURE FAILURE** (владелец жив → Recommended Action `run daemon recovery procedure first (see build skill)`) → скилл матчит метку **по префиксу** `run daemon recovery procedure first`, выполняет Daemon Recovery Procedure и делает **РОВНО ОДИН** ретрай (хирургически — kill только подтверждённого владельца).

**Подпроверки:** (a) префикс-матч полной метки агента против короткой в скилле. Подпункт (b) про пайп `jps -lv | grep` — СНЯТ (mesh-review 5/5 убрал пайпы; агент делает голые `jps`/`jstack`).

**Как навести lock-контенцию (нетривиально, «негативный кейс»):** запустить долгую Gradle-сборку в одном терминале (держит journal/cache lock в общем `~/.gradle`), затем параллельно триггернуть сборку через плагин против того же `~/.gradle`. Точную сигнатуру `Timeout waiting to lock` поймать непросто (тайминг) — возможно, понадобится эксперимент; СОГЛАСОВАТЬ подход с пользователем перед запуском.

**Осторожно:** сценарий 3 задействует recovery ГЛАВНОЙ сессии — там реальные `kill`/`ps`/`sleep`. Recovery хирургический: убивать ТОЛЬКО подтверждённого владельца лока из отчёта агента; чужие демоны (IDE/другие проекты/сессии) — не трогать.
