## claude (built-in self-review, fresh context)


Дизайн-ревью «build-runner Gradle hardening» (итерация 1). Прочитаны оба документа, все четыре целевых файла (agents/build-runner.md, skills/build/SKILL.md, README.md, CHANGELOG.md), локальный отчёт расследования (включая факты 8 и 11, на которые опирается протокол); все old_string плана сверены с фактическим содержимым файлов.

### Critical Issues

**1. План содержит несовпадающий old_string — Task 2 Step 1 не выполнится (или молча удалит текст).**
В фактическом файле skills/build/SKILL.md:53 жирное правило звучит как «Do not run ANY **build/test/lint/type-check** command directly…», а в плане и old_string, и new_string содержат усечённый вариант «build/test/lint command». Последствия двухступенчатые: Edit по несовпадающей строке упадёт, а если исполнитель «починит» вручную, ориентируясь на new_string из плана, из правила молча исчезнет «/type-check». Нужно исправить обе строки в плане до исполнения. Остальные old_string я сверил (frontmatter, Step 0/Step 1 агента, Build Commands, Maven-граница, Recommended Actions, guideline 12, README, CHANGELOG) — совпадают дословно; ошибка только эта.

**2. Механизм ожидания фоновой сборки не доведён до исполнимого состояния — а это сердце всего hardening.**
Протокол говорит: «не завершать ход, ждать уведомления, промежуточно читать файл вывода через Read». Проблемы:
- Субагент не может «просто ждать»: прекращение tool-вызовов означает завершение его работы (и, по факту 3 отчёта, осиротение/убийство фоновой сборки — та самая патология CANCELLED-демонов). Единственный способ «ждать» — цикл tool-вызовов. При этом sleep в whitelist агента отсутствует, то есть пейсинг невозможен: агент будет поллить с частотой раунд-трипа (сотни вызовов на 10–20-минутном остатке сборки).
- Инструкция «читать файл вывода через Read» без указания читать хвост (offset/limit) означает многократное перечитывание растущего Gradle-лога целиком — прямой путь к исчерпанию контекста агента именно в том сценарии, ради которого протокол писался. Умерший на переполнении контекста агент = осиротевшая сборка = возврат к исходной проблеме.
- Дешёвое решение лежит в уже выданных инструментах, но не прописано: статус-полл через Grep файла вывода по «BUILD SUCCESSFUL|BUILD FAILED|FAILURE:» (пустой результат — почти ноль токенов), Read хвоста только после совпадения, плюс добавить Bash(sleep:*) в whitelist (read-only-безопасно, философию «report, don't fix» не нарушает) и явную частоту поллинга (например, sleep 30 между пробами).
Без этих уточнений протокол «wait and report» на сборках длиннее 10 минут скорее всего деградирует в busy-loop или обрыв.

**3. Конфликт инструкций: Daemon Recovery Procedure требует от главной сессии запуска `./gradlew --stop`, который сама же связка скилл+агент категорически запрещает.**
Description скилла: «NEVER run build tools directly — always delegate»; жирное правило в теле: «Do not run ANY build/test/lint command directly». `./gradlew --stop` — буквально запуск build tool в главной сессии. Модель, исполняющая скилл, с заметной вероятностью либо откажется, либо «правильно» делегирует --stop агенту build-runner — которому новый Execution Rule 4 это прямо запрещает. Инструкционный тупик. Нужна явная однострочная оговорка в секции Daemon Recovery Procedure: команды процедуры (--stop, jps, kill, jstack) не являются build/test/lint-командами, выполняются главной сессией напрямую и никогда не делегируются build-runner.

### Concerns

**4. Секция README противоречит поведению агента после hardening.** Фраза «Without this any command longer than 2 minutes is moved to the background» становится неверной: агент теперь всегда передаёт явный timeout: 600000, и BASH_DEFAULT_TIMEOUT_MS на его сборки не влияет вовсе (явный timeout перекрывает дефолт). Хуже: рекомендация BASH_MAX_TIMEOUT_MS=1800000 не даёт эффекта, пока агент жёстко шлёт 600000 — явный per-call timeout не масштабируется от поднятого потолка автоматически. Реальные бенефициары этих env — команды главной сессии (включая recovery) и другие инструменты. Либо переформулировать «зачем» честно, либо решить вопрос повышенного timeout у агента (см. вопрос 1).

**5. Значение `orphaned background build` в enum Cause — висячий элемент.** Ни одна инструкция агента не описывает, когда его использовать. Логичный триггер — «агент вынужден вернуться до завершения фоновой сборки» (лимиты контекста/ходов), но такого escape-hatch в протоколе нет: там только «не завершай ход». При этом по отчёту завершение субагента осиротит/убьёт фоновую сборку — то есть escape-hatch сам провоцирует CANCELLED-демона, и вызывающему после такого отчёта нужен recovery-этикет (пауза перед ретраем). Либо описать явно: «если вынужден вернуться до конца сборки — INFRASTRUCTURE FAILURE, cause: orphaned background build, в Details ID задачи и путь к файлу вывода, Recommended Action: run daemon recovery procedure first», либо убрать значение из enum.

**6. Детекция инфра-сбоев покрывает только lock-timeout.** Другие частые демонные сигнатуры — «Gradle build daemon disappeared unexpectedly», «Could not connect to the Gradle daemon», «Daemon was stopped to free memory» — будут классифицированы как BUILD FAILED и получат до 3 ретраев от скилла с мгновенным повтором: ровно та лавина холодных демонов, от которой защищаемся. Добавить хотя бы daemon-disappeared/could-not-connect в Infrastructure Failures (пауза + один ретрай) дёшево и закрывает соседний класс отказов.

**7. `--console=plain` не доезжает до основного пути исполнения.** Правило добавляется в подсекцию «Build Commands» Gradle-секции, но Step 0 говорит «execute that exact task — skip Step 1»: агент, получивший «Run ./gradlew assembleDebug» (типовой случай — так его диспетчеризует скилл), до Gradle-секции может не дойти. Примеры Step 0 (assembleDebug, bundleRelease, ktlintFormat) остаются без флага. Правило нужно поднять в «Execution Rules (All Stacks)» («к любой ./gradlew-команде добавляй --console=plain»).

**8. «Ожидание» главной сессии тоже не специфицировано.** Dispatch discipline: «If an agent reports its build was moved to the background and is still running, wait for that build to finish before any new dispatch» — у главной сессии нет хэндла на процесс внутри умершего субагента; чем ждать (poll jps/ps с паузами? сколько?) не сказано. Аналогично «wait ~15 seconds» и «Wait 15–30 seconds» в recovery — указать механизм (sleep 15), иначе модель импровизирует. Для осиротевшей сборки честнее простое правило: сообщить пользователю и применить recovery-этикет, а не «ждать» неведомым способом.

**9. `jstack` выдан агенту, но не прописан к применению.** В инструкциях агента jstack не упоминается ни разу (он есть только в recovery-процедуре скилла, которую выполняет главная сессия своими правами). Либо прописать применение (например, при живом owner PID приложить в Details краткую выжимку jstack — верхние кадры), либо это мёртвый груз в whitelist, зафиксировать осознанно.

**10. Констрейнт «метки дословно» нарушается самим планом.** В скилле обработчик пишет «Recommended Action `run daemon recovery procedure first` (lock owner alive)» — без хвоста «(see build skill)». Функционально ок (префикс-матч), но глобальное ограничение требует дословного совпадения. Либо дописать хвост, либо ослабить формулировку констрейнта. Заодно: финальная сверка Task 4 Step 2 не грепает `safe to retry` в обоих файлах — из четырёх меток сверяются не все.

**11. Взаимодействие счётчиков попыток не определено.** «Maximum 3 build attempts for build/code errors; maximum 1 retry after an INFRASTRUCTURE FAILURE» — а смешанный сценарий (infra → recovery → ретрай → BUILD FAILED ktlint → ktlintFormat → …)? Считается ли инфра-ретрай в общие 3 попытки? Одна фраза снимет неоднозначность.

### Suggestions

1. **Протокол поллинга (к Critical 2):** конкретная последовательность в Execution Rules — sleep 30 (добавить Bash(sleep:*)) → Grep файла вывода по «BUILD SUCCESSFUL|BUILD FAILED|FAILURE:» → при совпадении Read хвоста (offset ближе к концу) → отчёт. Превращает декларацию «жди» в исполнимый цикл с предсказуемой стоимостью.
2. **Обновить секцию «Output format» скилла** (skills/build/SKILL.md:93-96): она перечисляет только BUILD SUCCESSFUL/BUILD FAILED; появляется третий формат — INFRASTRUCTURE FAILURE. Ни дизайн, ни план её не трогают.
3. **В Details инфра-отчёта агента** предписать приложить вывод jps (список живых демонов) — инструмент уже выдан, главной сессии это экономит шаг диагностики.
4. **Maven-симметрия:** -B/--batch-mode для mvn-команд — тот же мотив стабильного неинтерактивного вывода, что и --console=plain; одна строка в Maven-секции.
5. **README, idletimeout:** одна строка про трейдофф (после 30 минут простоя первая сборка снова холодная) — сейчас рекомендация выглядит бесплатной.
6. **Процессные шаги плана:** нет напоминания про пользовательский workflow «перед PR — git rm docs/superpowers/* и коммит» (глобальный CLAUDE.md); и план фиксирует session-трейлер сессии планирования, тогда как правило харнеса велит исполнителю подставлять URL своей сессии — при исполнении в свежей сессии возникнет конфликт, стоит явно решить, какой трейлер канонический.
7. **Смоук-тест:** добавить негативный сценарий — искусственно занять lock (или фейковый owner PID) и убедиться, что агент выдаёт INFRASTRUCTURE FAILURE с верным Recommended Action, а скилл выполняет ровно один ретрай.

### Questions

1. Что делает харнес при явном timeout больше BASH_MAX_TIMEOUT_MS — клипует до потолка или отклоняет вызов? Если клипует, агент может всегда передавать 1800000, и рекомендация BASH_MAX_TIMEOUT_MS в README начнёт реально работать; если отклоняет — хардкод 600000 остаётся единственным безопасным вариантом, и README нужно переписать (см. Concern 4). Факт 11 отчёта покрывает «per-call работает до потолка», но не поведение сверх него.
2. Подтверждено ли расследованием, что уведомление о завершении фоновой задачи доставляется внутрь субагентного диалога (а не только в главную сессию)? Факт 11 подтверждает файл вывода и увод в фон, но «wait for the task-completion notification» опирается на недоказанный канал; если его нет, протокол должен честно опираться только на поллинг.
3. Доступен ли sleep в целевой среде агента и готовы ли добавить Bash(sleep:*) в whitelist? Без него пейсинг ожидания невозможен в принципе (см. Critical 2).
4. Правильно ли я понимаю по отчёту, что завершение субагента убивает уведённую в фон сборку (а не оставляет её жить)? От этого зависит дизайн escape-hatch из Concern 5: если убивает — каждый ранний возврат гарантированно производит CANCELLED-демона, и recovery-этикет после «orphaned background build» обязателен, а не опционален.
5. Сознательно ли INFRASTRUCTURE FAILURE ограничен Gradle? Формат объявлен в «Error Reporting Format (All Stacks)», а детекция есть только в Gradle-секции; у npm (EBUSY/cache lock) и go (build cache lock) есть свои инфра-сигнатуры. Если ограничение сознательное — стоит строчка «for other stacks report as BUILD FAILED», чтобы агент не изобретал формат сам.

**Итог:** диагноз и направление правок убедительны и хорошо опираются на верифицированные факты; блокируют исполнение три вещи — битый old_string в Task 2 (пункт 1), невыполнимый в текущем виде механизм ожидания фоновой сборки (пункт 2) и инструкционный тупик вокруг `./gradlew --stop` (пункт 3). Все три чинятся точечными правками документов без пересмотра принятых решений.

## codex-executor (gpt-5.6-sol, reasoning max)


Вердикт Codex: документы пока не готовы к реализации — есть блокирующие проблемы жизненного цикла сборки и небезопасная процедура восстановления; файлы не изменялись.

### Critical Issues

1. **10-минутный timeout не ограничивает время выполнения.** После 600 секунд команда лишь уходит в фон, после чего агент обязан ждать её без ограничения и не завершать ход (design:34, plan:73). Для настоящего зависания terminal state отсутствует. При синхронной диспетчеризации main-session ждёт агента, агент ждёт Gradle, поэтому ветка «If it hangs again: capture `jstack`» практически недостижима (plan:314). Нужен отдельный wall-clock deadline и явная передача управления main-session.

2. **Daemon Recovery Procedure может убить здоровые чужие сборки.** `ps -p X` подтверждает только существование PID, но не то, что это Gradle daemon, что он завис и относится к текущему проекту (plan:153). Затем `./gradlew --stop` затрагивает все доступные демоны той же версии, а `jps` → `kill` — вообще всех найденных Gradle/Kotlin daemon текущего пользователя (plan:308). Это опасно при параллельной работе IDE, другого проекта или другой Claude-сессии. Нет проверки command line/start time/owner, защиты от PID reuse и подтверждения пользователя перед `kill -9`.

3. **Заявленный межфайловый контракт уже нарушен самим планом.** План требует дословного совпадения четырёх маркеров (plan:21), но consumer использует сокращённое `run daemon recovery procedure first` без `(see build skill)` (plan:287). В предлагаемом тексте агента также нет точной метки `Daemon Recovery Procedure` с таким регистром. Кроме того, нижняя секция `Output format` скилла остаётся только с `BUILD SUCCESSFUL` и `BUILD FAILED` (skills/build/SKILL.md:93); план не добавляет туда `INFRASTRUCTURE FAILURE`.

4. **README противоречит явному per-call timeout.** Агент всегда передаёт `timeout: 600000`, поэтому `BASH_DEFAULT_TIMEOUT_MS=600000` на его сборки не влияет, а `BASH_MAX_TIMEOUT_MS=1800000` лишь разрешает больший timeout, которого агент никогда не запрашивает (plan:73). Следовательно, фраза «Without this any command longer than 2 minutes is moved to the background» неверна для обновлённого build-runner: без настройки он уйдёт в фон после 10 минут, и с настройкой — тоже после 10 минут (plan:384).

5. **Контракт INFRASTRUCTURE FAILURE неполон.** Формат допускает `orphaned background build` и `other environment issue` (plan:186), но единственная описанная детекция — lock timeout с Owner PID. Не определено: (a) как агент обнаруживает orphaned build, если он обязан не завершаться; (b) какое действие выбирать для `other environment issue`; (c) что делать при отсутствующем PID, отказе `ps` или живом не-Gradle процессе; (d) как main-session получает ID/output path фоновой задачи. В результате произвольная инфраструктурная ошибка может ошибочно запустить уничтожение демонов.

6. **Верификация пропускает известные нарушения.** Проверяется количество `console=plain`, а не каждая Gradle-команда; точное action-value проверяется укороченным substring; команда проверки `kill` не анализирует именно frontmatter и возвращает успешный exit status в обоих исходах (plan:217, plan:338). Единственный поведенческий smoke-test отложен «после мержа» (design:119), хотя он проверяет главный риск всей архитектуры.

### Concerns

1. `--console=plain` добавляется лишь в три шаблона, тогда как обычные запросы скилла передают точную команду `Run ./gradlew ...`, а Step 0 требует выполнить её точно и пропустить detection (agents/build-runner.md:13, skills/build/SKILL.md:19). Нормальный путь может вообще не применить новое правило. Также не определено поведение, если пользователь уже передал другой `--console`.

2. Последовательность действует только внутри одного вызова build-skill. Другие Claude-сессии, IDE и терминалы продолжают параллельно использовать общий `~/.gradle`, то есть архитектура устраняет самодублирование, но не гарантирует глобальную сериализацию.

3. `jps` и `jstack` добавляются агенту, но его lock-протокол использует только `ps`; `jps`/`jstack` фактически вызываются main-session (plan:53, plan:155). Не описаны отсутствие этих утилит в PATH, attach failure или timeout самого `jstack`.

4. Глобальная рекомендация `auto-detect=false` с жёсткими путями только к Zulu 17/21/25 может сломать остальные Gradle-проекты пользователя, которым нужны JDK 8/11 или иной layout (plan:399). Снижение daemon idle timeout до 30 минут также увеличивает число холодных стартов — это стоит описать как компромисс, а не безусловное улучшение.

5. Не определено, что считается «attempt»: исходная сборка, `ktlintFormat`/`ruff --fix`, повтор после форматирования и инфраструктурный retry. Формулировка «3 attempts for build/code errors плюс 1 infra retry» допускает разные трактовки и больше четырёх запусков (plan:319).

6. Не зафиксированы минимальная версия Claude Code и поддерживаемые платформы. Протокол зависит от поведения 2.1.210+, а recovery использует POSIX `ps`/`kill`. Отдельно нужны правила для заведомо долгоживущих задач вроде `bootRun`, watch-mode и действительно зависших тестов.

### Suggestions

1. Описать конечный state machine: `FOREGROUND_RUNNING → BACKGROUND_RUNNING → COMPLETED | OBSERVATION_DEADLINE_EXCEEDED`. Для последнего состояния агент должен передавать task ID, output path, команду и диагностированные PID, после чего main-session прекращает точную фоновую задачу документированным механизмом и только затем запускает recovery. Запрет `kill` для агента при этом сохраняется.

2. Сузить recovery до подтверждённого владельца: `ps -o user,pid,ppid,lstart,stat,etime,args`, `jps -lv`, по возможности `jstack` до уничтожения; повторная проверка identity перед сигналом. Не убивать все `GradleDaemon`/`KotlinCompileDaemon` автоматически. Если процесс относится к другой активной сборке — сообщать пользователю и запрашивать решение.

3. Добавить стабильные машинные коды, сохранив обязательные человекочитаемые строки, например `STATUS: INFRASTRUCTURE_FAILURE` и `ACTION: SAFE_TO_RETRY | DAEMON_RECOVERY_REQUIRED`. Это уменьшит зависимость от регистра и поясняющего текста модели.

4. ## ext-claude-executor (alibaba/qwen — Qwen 3.7 Plus)


Прочитал оба документа и текущее состояние файлов (`agents/build-runner.md`, `skills/build/SKILL.md`, `README.md`, `CHANGELOG.md`). Ниже — критический разбор.

## Critical Issues

### 1. `timeout: 600000` жёстко в Execution Rules — но есть и host setup в README
Правило 1 («MUST pass `timeout: 600000`») противоречит логике секции Recommended host setup: если пользователь настроил `BASH_DEFAULT_TIMEOUT_MS=600000`, то агент всё равно обязан передавать таймаут вручную. Получаем две параллельные системы с разными единицами (мс в env, «10 минут» в правиле) и рассинхронизацией: кто-то поправит env на 30 минут, а агент по-прежнему будет ставить 10.

**Риск:** двойной источник правды → путаница при отладке («я настроил хост, почему агент всё равно ограничен 10 минутами?»).

**Как лечить:** либо (а) в правиле написать «pass `timeout: 600000` (or a higher value for known-slow builds; if the host has `BASH_DEFAULT_TIMEOUT_MS` configured, that value applies to calls without an explicit timeout — but explicit is still safer)», либо (б) сделать правило мягче: «always pass an explicit timeout; 600000 is the default floor, raise it for known-slow projects». В текущем виде правило слишком догматично и не учитывает, что у некоторых проектов сборка реально идёт 20+ минут.

### 2. `jps` / `jstack` в PATH — неочевидно
Агент использует `export JAVA_HOME=/usr/lib/jvm/zulu<N>` и вызывает `./gradlew`. Но `jps` и `jstack` — это `$JAVA_HOME/bin/jps`, не всегда в PATH. Если у пользователя в PATH system JDK, а проект собирается под другим JDK, `jps` может показать демонов system JDK, а не проекта.

**Риск:** агент найдёт не тот PID → диагностика неверна → либо false «owner dead», либо false «owner alive».

**Как лечить:** в разделе Infrastructure Failures явно указать: «run `$JAVA_HOME/bin/jps` / `$JAVA_HOME/bin/jstack <pid>`». Или добавить в Execution Rules замечание, что для JDK-утилит надо использовать полный путь.

### 3. Нет upper bound на ожидание фоновой сборки агентом
Execution Rule 3: «Do not end your turn while the build is still running». Но что если сборка реально зависла (а не просто превысила дефолт 120 с)? Агент будет ждать бесконечно, съедая tokens и context. В текущем тексте нет:
- максимального времени ожидания;
- инструкции что делать, если уведомление о завершении так и не пришло (пользователь убил, харнес потерял связь);
- ограничения на число Read-циклов output-файла.

**Риск:** sonnet-агент застревает на 30+ минут, жжёт токены на пустые Read'ы, сессия фактически зависает.

**Как лечить:** добавить: «Wait up to ~15 minutes total for a backgrounded build. If the task is still running after that, report INFRASTRUCTURE FAILURE (orphaned background build) and stop».

### 4. `--console=plain` покрыт только для трёх команд в Build Commands
Task 1 Step 3 добавляет `--console=plain` к `build`, `build -x test`, `clean build`. Но агент вызывает и другие Gradle-команды: `test`, `lintDebug`, `ktlintFormat`, `assembleDebug`, `bundleRelease`, и т.д. Для них правило не сформулировано — в Execution Rules тоже нет общего «always append `--console=plain` to ANY Gradle invocation».

**Риск:** часть вызовов пойдёт без `--console=plain`, парсинг логов вернётся к старым проблемам с ANSI/in-place updates.

**Как лечить:** вынести правило в Execution Rules как общее (для всех Gradle-вызовов, не только для «Build Commands»), а в Build Commands оставить как пример.

### 5. Классификация INFRASTRUCTURE FAILURE vs BUILD FAILED — на откуп LLM
Агент (даже sonnet) должен сам решать, инфра-сбой это или код. Ошибки классификации:
- **False INFRASTRUCTURE FAILURE** (реальный build failure помечен как инфра) → скилл выполнит Daemon Recovery Procedure, потеряет время, сделает retry → снова BUILD FAILED → и только тогда остановится. Итого: потеря 1–2 минут на kill демонов зря.
- **False BUILD FAILED** (реальный infra помечен как код) → скилл просто покажет ошибку, recovery не запустится, проблема останется.

В spec есть только один конкретный паттерн («Timeout waiting to lock … Owner PID: X»). А что с другими: `Timeout waiting to acquire shared lock on build queue`, `Could not resolve all files for configuration`, `java.net.SocketTimeoutException`, `Daemon disappeared`? Они все попадают в «other environment issue» — но это слишком размыто.

**Риск:** LLM будет галлюцинировать классификацию на граничных кейсах; recovery procedure запустится ложно.

**Как лечить:** (а) в разделе Infrastructure Failures дать более полный список паттернов с цитатами; (б) добавить правило: «If unsure, classify as BUILD FAILED (do not trigger daemon recovery on uncertain grounds)»; (в) в скилле — не слепо доверять Recommended Action, а минимум проверять, что INFRASTRUCTURE FAILURE действительно содержит корректный Owner PID и его статус.

## Concerns

### 6. Фиксированная пауза 15–30 с в Daemon Recovery Procedure
Текст: «Wait 15–30 seconds before retrying». Но LLM не умеет «15–30» — она либо подождёт 15, либо 30, либо (что вероятнее) пропустит sleep, т.к. у неё нет нативной команды sleep и Bash-вызов `sleep 20` потребует явной инструкции.

**Риск:** в реализации LLM может не вставить `sleep` вообще, и пауза окажется нулевой.

**Как лечить:** явно прописать команду: `sleep 20` (bash). Не «wait 15–30 seconds», а конкретный вызов.

### 7. `./gradlew --stop` — но у проекта может не быть `gradlew`
Если скилл вызван для Maven-проекта, или для чистого Gradle-проекта без wrapper (редкость, но бывает), команда `./gradlew --stop` не работает. Нужно fallback на системный `gradle --stop` или проверка существования `gradlew`.

### 8. `Bash(jps:*)` / `Bash(ps:*)` / `Bash(jstack:*)` — permission granularity
В Claude Code паттерн `Bash(tool:*)` матчится по префиксу команды. Если агент напишет `/usr/lib/jvm/zulu21/bin/jps -l`, паттерн `Bash(jps:*)` не сматчится — команда начинается не с `jps`. Это усугубляет проблему 2.

**Как лечить:** либо разрешить `Bash(*jps:*)` (если поддерживается), либо явно инструктировать агента вызывать утилиты через `$(which jps)` или `$JAVA_HOME/bin/jps` с соответствующим permission pattern, либо добавить `Bash(*/jps:*)`.

### 9. `kill <pid>` в Daemon Recovery Procedure выполняется в главной сессии
Главная сессия получает право убивать процессы — но у неё тоже permission model. Нужно убедиться, что у пользователя в settings.json разрешён `Bash(kill:*)` или аналог. В README про это ни слова — пользователь, настроивший «Recommended host setup», может столкнуться с prompt'ом на каждый `kill`.

### 10. «Dispatch is strictly sequential» — enforcement только словами
Это директива LLM, не механизм. Если claude code решит запустить два билда параллельно (например, пользователь быстро попросил два раза), ничего его не остановит. Нет счётчика, нет блокировки.

**Риск:** при высокой нагрузке/стресс-тестах LLM может нарушить правило. Это осознанное ограничение («мы не можем закодировать enforcement в markdown»), но стоит явно признать в спеке.

### 11. `docs/gradle-build-runner-hardening-report.md` untracked — но может быть случайно закоммичен
В Global Constraints: «never `git add docs/` or `git add -A`». Это instruction LLM. При ошибке или при использовании `git commit -am` отчёт уедет в PR. Нет программной защиты (`.gitignore`, например).

**Как лечить:** добавить `docs/gradle-build-runner-hardening-report.md` в `.gitignore` (или `docs/*-report.md`). Или удалить после ревью.

### 12. Sonnet-модель — стоимость на длинных сборках
haiku ≈ $0.001/1K in, $0.002/1K out; sonnet ≈ $0.003/1K in, $0.015/1K out. На сборке с 50K логами и несколькими retry разница существенна. Для пользователя, который гоняет build-runner 20 раз в день, это может добавить $5–10/день.

**Это не блок**, но в README стоит упомянуть cost-компромисс, чтобы пользователи делали информированный выбор.

### 13. Task 1 Step 5 — формат INFRASTRUCTURE FAILURE вложен в Error Reporting Format
Но в Error Reporting Format уже есть `On Success` и `On Failure`. INFRASTRUCTURE FAILURE — третий формат, но расположен ПОСЛЕ `## Important Guidelines`? Проверим: в Task 1 Step 5 old_string заканчивается `## Important Guidelines`, и новый блок вставляется **перед** Important Guidelines. Это нормально, но порядок секций в итоговом файле будет: Success / Failure / INFRASTRUCTURE FAILURE / Important Guidelines. Ок, логично. Но в плане это не очевидно — можно пропустить.

### 14. `run daemon recovery procedure first (see build skill)` — длинная метка
45 символов, в agent-отчёте может быть случайно перефразирована (LLM любит синонимизировать). Чем короче и уникальнее маркер, тем надёжнее парсинг в скилле.

**Как лечить:** использовать более короткий и менее «человеческий» маркер: `RECOVERY_REQUIRED` или `RUN_DAEMON_RECOVERY`. А в скилле матчить по нему. Но это уже поздно — решение зафиксировано пользователем. Тогда хотя бы в агенте указать: «use this exact phrase verbatim; do not paraphrase».

**1. Битый якорь Edit в Task 2 Step 1 — план разойдётся с файлом на первом же шаге Task 2**

План цитирует old_string:

> `**Do not run ANY build/test/lint command directly — always delegate…**`

Фактический текст в `skills/build/SKILL.md:53`:

> `**Do not run ANY build/test/lint/type-check command directly — always delegate…**`

В файле есть `/type-check`, в плане (и в old_string, и в new_string!) — нет. Последствия:
- Edit по дословному old_string упадёт → исполнитель остановится (в лучшем случае) или начнёт «чинить» сам.
- Хуже: если исполнитель возьмёт new_string из плана как эталон, из скилла молча пропадёт `/type-check` — регрессия формулировки, согласованной с description агента (`agents/build-runner.md:3`, где `/type-check` есть).

Надо пересинхронизировать Step 1 Task 2 с фактическим файлом. Остальные якоря плана проверены дословно — совпадают; сломан только этот.

**2. Протокол «ждать фоновую сборку» не обеспечен инструментами: у агента нет механизма ожидания и нет предела ожидания**

Правило 3 Execution Rules велит «wait for the task-completion notification; check interim progress with Read; do not end your turn». Но:

- В tools агента нет ничего, чем можно «ждать»: ни `Bash(sleep:*)` (Bash ограничен build-инструментами + jps/jstack/ps), ни TaskOutput/BashOutput. Уведомление о завершении приходит только между tool-вызовами, значит агент обязан непрерывно что-то вызывать. Единственный доступный «poll» — Read файла вывода, без какой-либо каденции. Для 20–40-минутной сборки это busy-loop: десятки Read'ов растущего Gradle-лога → сжигание токенов и раздувание контекста субагента (риск умереть от переполнения — то есть снова нарушить протокол, который чиним).
- Ожидание не ограничено сверху. При этом подтверждённый факт 7 (вечный хэнг автодетекта тулчейнов — сборка висит бесконечно без вывода) в runtime вообще не обрабатывается: агент будет поллить вечно. Единственная защита от факта 7 — рекомендательная строка в README.
- Из-за этого не работает и шаг 5 Daemon Recovery Procedure: «If it hangs again: capture jstack…» — главная сессия никогда не узнает, что «hangs again», потому что ни у агента, ни у скилла нет определения «завис» и нет отчёта для этого состояния.

Минимально необходимое: (a) механизм ожидания — добавить `Bash(sleep:*)` (инертно, не конфликтует с решением «только read-only диагностика», которое было про kill) и/или явную каденцию «Grep файла вывода на `BUILD SUCCESSFUL|BUILD FAILED|FAILURE:` вместо полного Read»; (b) предел ожидания и детектор застоя (вывод не растёт N минут → отчёт `INFRASTRUCTURE FAILURE / Cause: stalled build` с task ID); (c) соответствующая ветка обработки в SKILL.md. Бонус: ограниченный give-up замыкается на уже спроектированную механику — осиротевшая живая сборка при следующем запуске даст lock timeout с живым Owner PID → recovery.

**3. Обоснование секции README противоречит новому поведению агента (несостыковка Изменений 1 и 3)**

После Task 1 агент **всегда** передаёт явный `timeout: 600000`. Значит:
- `BASH_DEFAULT_TIMEOUT_MS=600000` больше не влияет на сборки плагина вообще — фраза README «Without this any command longer than 2 minutes is moved to the background mid-build» становится фактически ложной ровно для тех сборок, ради которых секция написана. Реальная ценность — страховка на случай, если модель забудет параметр, и команды вне плагина.
- `BASH_MAX_TIMEOUT_MS=1800000` не используется никем: ничто в плагине не запрашивает больше 600000. Потолок 30 минут «включится» только если пользователь ещё и форкнет агента. В отчёте-расследовании эта связка была («тогда агенту можно разрешить timeout до 1800000»), в дизайн она не перенесена — осталась половина рекомендации без второй половины.

Секцию нужно либо переписать честно (safety net + «потолок пригодится, если поднять timeout в форке агента»), либо решить вопрос с запросом >600000 на стороне агента (см. Questions про clamp). Заодно упомянуть побочный эффект глобального `BASH_DEFAULT_TIMEOUT_MS=600000`: любая случайно повисшая интерактивная команда (git, ждущий credentials) теперь держит форграунд 10 минут вместо 2 — аргумент в пользу project-scope настройки.

### Concerns

**4. Daemon Recovery Procedure игнорирует Owner PID, который агент только что определил.** Агент диагностирует конкретный PID держателя лока (жив/мёртв), а процедура восстановления его не использует: `--stop` → `jps` → убить **всех** выживших `GradleDaemon`/`KotlinCompileDaemon`. Это сносит демонов чужих проектов и IDE (IntelliJ Gradle sync — тоже GradleDaemon в jps), т.е. лечение одной сборки ломает соседние. Хирургичнее: сначала `kill <Owner PID из отчёта>`, blanket-kill — как эскалация. Мелочь там же: в шаге 5 `jstack <daemon pid>` — после шага 3 все старые демоны мертвы, PID нового демона надо заново искать через `jps`, шаг об этом молчит.

**5. «If an agent reports its build was moved to the background and is still running, wait for that build to finish before any new dispatch» (Dispatch discipline) — неоперационализируемая инструкция.** По новому протоколу агент не должен возвращаться, пока сборка идёт, — значит, эта ветка срабатывает только при нарушении протокола или смерти субагента. Но у главной сессии нет ни хэндла фоновой задачи субагента, ни описанного способа «ждать» (по отчёту задача при завершении хода субагента осиротевает/убивается — и тогда ждать нечего). Инструкцию нужно либо конкретизировать (чем проверять: `ps`/`jps`? сколько ждать?), либо заменить маршрутизацией: «агент вернулся, а сборка ещё шла → трактовать следующий сбой как INFRASTRUCTURE FAILURE с живым владельцем → recovery».

**6. Детекция инфра-сбоев заточена под одну сигнатуру, которой в логах ноль за 30 дней.** «Timeout waiting to lock» — обоснованная защита в глубину, но реально встречающиеся инфра-сигнатуры не замаплены: `Gradle build daemon disappeared unexpectedly` (упавший/OOM-killed демон), ERROR-вариант «Timeout waiting to lock daemon addresses registry» (факт 6 различает DEBUG и ERROR — в агенте описан только DEBUG-шум), крэш Kotlin compile daemon. Все они уйдут в `BUILD FAILED` → главная сессия применит этикет ретраев для ошибок кода (до 3 попыток без пауз) — ровно то, чего для инфра-сбоев старались избежать. Плюс: значение Cause `orphaned background build` объявлено в формате отчёта, но ни одно правило его не производит — мёртвый элемент enum'а.

**7. `--console=plain` не достигает главного пути исполнения.** Правило живёт внутри секции «Gradle Stacks → Build Commands», но самый частый путь — Step 0 («caller specifies a concrete command → execute that exact task»): скилл диспетчеризует буквально «Run ./gradlew build», и агент, следуя «execute that exact task», секцию Build Commands не открывает. Две инструкции прямо конфликтуют. Правило должно стоять в Execution Rules (All Stacks) с оговоркой «для Gradle-команд».

**8. Сборки длиннее 10 минут теперь систематически идут фоновым путём** — Android release с R8/минификацией легко превышает 600 с. Протокол это переживает, но фоновый путь становится *штатным* для release-сборок, а смоук-тест покрывает только «сборка >2 мин». Нужен второй смоук-кейс: сборка >10 мин → уход в фон → агент дождался и отчитался, ничего не перезапустив.

**9. Верификация проверяет наличие текста, а не согласованность меток.** Global Constraints требуют дословного совпадения `safe to retry` и `run daemon recovery procedure first (see build skill)` между файлами, но: (a) ни один grep эти строки не проверяет; (b) в SKILL.md метка сознательно усечена до `run daemon recovery procedure first` без «(see build skill)» — т.е. заявленное «дословно» на самом деле «по подстроке». Решение разумно, но констрейнт и проверки должны честно это фиксировать, иначе исполнитель плана «восстановит согласованность» не в ту сторону.

**10. Учёт ретраев не согласован.** «Maximum 3 build attempts for build/code errors; maximum 1 retry after an INFRASTRUCTURE FAILURE» — а если инфра-сбой случился на попытке 2 из 3? Инфра-повтор входит в бюджет трёх? Может ли за сессию быть 3 build-ретрая + 1 инфра-ретрай + recovery? Нужно одно предложение с явной арифметикой.

---

### Suggestions

- **Расширить правило таймаута на установку зависимостей.** «Every Bash call that runs a build/test/lint command» буквально не покрывает `npm install`, `uv sync`, `poetry install`, `pip install -r` — команды, которые рутинно превышают 120 с и уйдут в фон по дефолту. Переформулировать: «any potentially long-running command, including dependency installs».
- **Poll через Grep, а не Read.** Grep уже в tools; проверка «файл вывода содержит `BUILD SUCCESSFUL|BUILD FAILED|FAILURE:`» на порядок дешевле для контекста; Read с offset — только для финального отчёта.
- **Смоук-тест до мержа, а не после.** README сам документирует `claude --plugin-dir` — логично прогнать оба смоук-кейса из ветки до мержа.
- **Замапить `daemon disappeared unexpectedly` → INFRASTRUCTURE FAILURE / `safe to retry`** — дешёвое расширение, закрывает самый частый реальный инфра-кейс.
- **Плейсхолдер вместо захардкоженного URL сессии.** План фиксирует `Claude-Session: …session_01JT…` сессии планирования; execution prompt это переопределяет, но план — самостоятельный документ. В плане должно быть `<URL текущей сессии>`.
- **Одна строка в README про `jps` на PATH.** Диагностика и recovery молча предполагают, что `jps` доступен (на машинах, где JDK только в `/usr/lib/jvm/...`, его нет в PATH).
- **Указать в recovery, что повтор после восстановления будет медленным** (холодный демон + холодный Kotlin daemon) — иначе «медленный ретрай» рискует быть принят за рецидив зависания.

---

### Questions

1. **Что делает харнес при per-call `timeout` > `BASH_MAX_TIMEOUT_MS` — клампит или ошибка?** Если клампит, агенту можно писать `timeout: 1800000` (деградирует до 600000 на ненастроенном хосте, использует 30 минут на настроенном) — и README-рекомендация `BASH_MAX_TIMEOUT_MS` обретает смысл без форка. Факт 11 отчёта это не покрывает.
2. **Доступны ли субагенту TaskOutput/BashOutput и доживает ли его фоновая задача до конца хода?** Отчёт утверждает «осиротевает/убивается», но помечает это интерпретацией — от ответа зависят Critical #2 и Concern #5.
3. **Сборки >10 минут — штатный кейс?** Если да (Android release), принять фоновый путь как норму и задокументировать, или держать типовые сборки в форграунде через повышенный timeout (см. вопрос 1)?
4. **Как считается бюджет попыток при смешанных сбоях** (инфра-сбой посреди серии build-ошибок) — см. Concern #10?

**Итог.** Дизайн бьёт точно в подтверждённую первопричину, связка «агент диагностирует — сессия лечит» архитектурно чистая. До исполнения обязательны три вещи: пересинхронизировать якорь Task 2 Step 1 с фактическим текстом SKILL.md (иначе план падает и грозит регрессией `/type-check`), дать агенту реальный механизм и предел ожидания фоновой сборки (иначе центральный протокол держится на busy-poll без выхода из вечного зависания), и привести README-секцию в соответствие с новым поведением агента.

# Обзор: build-runner Gradle Hardening (design + plan)

## Critical Issues

### C1. Команда в `Execution Rules` запрещает перезапуск, но не объясняет, что делать с **уже** осиротевшими фоновыми процессами при выходе
В `Execution Rules (All Stacks)` шаги 3–4 (план, Task 1, Step 2) говорят: «жди уведомления, не завершай ход, не перезапускай». Но **что если агент уже завершил ход** (например, предыдущая попытка до применения патча)? У агента нет инструкции по сценарию «фоновый процесс уже жив, его ID мне известен из прошлого ответа — как отменить?» — и не должно быть (нет `kill` в tools). Но это значит, что при первом развертывании патча какое-то время в проде будут жить осиротевшие сборки, которые новый диспетчер увидит как `build-runner is still running`. Где скилл должен это явно показать? В плане — нигде. **Нужна явная ветка в Step 2 скилла**: «if a previous agent reports its build was moved to background, wait; if the user reports a stuck build, run Daemon Recovery Procedure».

### C2. `--console=plain` добавлен в `Build Commands` агента, но в `Step 0` пользователь часто задаёт команду напрямую (например, "run npm test") — патч не покрывает прямой путь
В `Step 0` сказано: «execute that exact task — skip stack detection». Например, промпт «run npm test» → агент вызывает `npm test` без `--console=plain`, что для Gradle не нужно, но при этом **обходятся все Execution Rules** на этапе выбора команды. Сейчас Execution Rules сформулированы как «apply to EVERY build/test/lint command» — норм, но фактический пример в `Step 0` про `npm test` показывает, что правила не подкреплены явной связкой «Step 0 → Execution Rules тоже применяются». Если haiku/sonnet пройдёт мимо — а на длинных логах именно это и происходило — патч бесполезен. **Нужна явная отсылка `Step 0: ... subject to the Execution Rules above`**.

### C3. План ссылается на метрики, которые не зафиксированы в acceptance criteria
В acceptance criteria дизайна (раздел «Критерии приёмки»): «`console=plain` — 4 совпадения». В плане (Task 1, Step 3) фактически делается 3 команды + 1 преамбула. Но преамбула («Append `--console=plain` to every Gradle invocation...») находится **вне bash-блока**, и если редактор потеряет эту строку, grep даст 3 совпадения — и всё равно «ok». Хрупкая верификация. **Нужно** `grep -c "console=plain" == 4 || fail`.

### C4. Plan оставляет `--console=plain` как «опционально; вне проверенных фактов» (отчёт, секция A.8), но дизайн/план добавляют его как обязательный — расхождение
В `docs/gradle-build-runner-hardening-report.md` помечено: «опционально; вне проверенных фактов — добавлять `--console=plain`». В дизайне — добавляется как обязательная правка. В плане — тоже обязательная. Документы консистентны между собой, но противоречат базовому отчёту. **Нужно решение**: либо (а) повысить статус «опционально» до «обязательно» с обоснованием, либо (б) убрать из патча и оставить на усмотрение. Сейчас висит в воздухе.

### C5. `Daemon Recovery Procedure` предписывает `jps` главной сессии — но у главной сессии **тоже нет `Bash(jps:*)` в правах по умолчанию**
Агент получает `Bash(jps:*)`. Главная сессия (main session, она же host) в типичной инсталляции Claude Code имеет **все** Bash-права (это не плагин-агент). Но дизайн этого не проговаривает. Если пользователь сидит в проекте, где `~/.claude/settings.json` ограничивает `Bash(...)` для main session, шаги 2–3 процедуры восстановления потребуют **два** разовых промпта-разрешения — это перечеркнёт «15–30 секунд пауза» (пользователь может уйти). **Нужна** рекомендация в README: «Daemon Recovery Procedure requires unrestricted Bash in the main session; allow `Bash(jps:*)`, `Bash(kill:*)`, `Bash(jstack:*)` (or allow all)».

### C6. «Maximum 1 retry after an INFRASTRUCTURE FAILURE» в скилле не учитывает **уже** сделанные попытки при code errors
В `Limitations` (план, Task 2, Step 4) написано: «Maximum 3 build attempts for build/code errors; maximum 1 retry after an INFRASTRUCTURE FAILURE». Но в Step 2 (план, Task 2, Step 2) ветка обработки «INFRASTRUCTURE FAILURE» срабатывает в **середине** попыток — итого может быть 3 code + 1 infra = 4 попытки. Или хуже: 2 code + 1 infra + ещё 2 code = 4. **Не определена общая граница попыток**. Нужна единая семантика: «максимум 4 попытки всего; среди них максимум 1 — после INFRASTRUCTURE FAILURE».

## Concerns

### N1. Дизайн не определяет, как агент должен себя вести при **нескольких** последовательных уходах в фон
Сценарий: haiku/sonnet запустил сборку, ушла в фон, агент ждёт. Но у агента может быть лимит длительности хода (tool-timeout harness). Если сборка идёт 5 мин, а ход агента упирается в лимит — что произойдёт? Дизайн не отвечает. Если лимит на ход агента — 5 мин (типично), то «жди уведомления» не работает в принципе. **Нужно** либо: (а) увеличить лимит хода через харнес, (б) документировать ограничение, (в) использовать другой механизм (например, `TaskOutput`).

### N2. Ссылка `(see build skill)` в агенте — это **обычный текст**, не структурная ссылка
Если кто-то переименует секцию в скилле (например, `## Daemon Recovery Procedure` → `## Daemon Cleanup`), ссылка «(see build skill)» всё ещё «жива», но больше не указывает на конкретную секцию. **Лучше** использовать анкор-ссылку или явно назвать «see the `Daemon Recovery Procedure` section of the `build` skill». План уже фиксирует точные строки — но только «see build skill» обретает новый смысл при будущих правках. Добавьте в Step 3 плана: «ссылка должна включать имя секции».

### N3. Step 1 скилла (план) описывает диспетчеризацию build-runner с промптом «Run ./gradlew build», но не учитывает, что **промпт сам по себе** должен включать контекст
Если сессия main передаёт агенту промпт «Run ./gradlew build» и через минуту меняет запрос, build-runner уже работает — и у скилла нет протокола «агент уже диспетчеризован, новые требования — отменяем, обновляем, или ждём». **План вводит «Dispatch discipline»** (один build-runner за раз) — но не «новый промпт в полёте = ?». Edge case для крупных проектов: пользователь часто уточняет «а добавь ещё ktlintCheck». Без протокола агент проигнорирует уточнение, либо (что хуже) отрапортует по старой команде.

### N4. `--console=plain` — в Gradle 8+ это уже дефолт для неинтерактивного режима, но при `gradlew build` без `TERM=dumb` он переключается на rich console
Точнее: в Gradle 9+ `--console=plain` действительно стабилизирует вывод, но `BASH` наследует `TERM` от терминала, и `--console=auto` (по умолчанию) может давать **ANSI escape codes**, ломающие парсинг. Правильно. **Однако**: при фоновом запуске в Bash-инструменте Claude Code `TERM` может быть не задан, и `--console=plain` избыточен. **Лучше** `--no-daemon=false --console=plain --no-build-cache=false` или `FORCE_COLOR=0` через env. Не критично, но стоит проверить эмпирически, действительно ли `plain` даёт стабильный парсинг.

### N5. `Bash(jstack:*)` агенту — но jstack требует JDK, а агент узнаёт JAVA_HOME только на Step 2
Агент узнаёт `JAVA_HOME` в Step 2, но при работе в новой shell-calls может не экспортировать. `jstack` должен лежать в `$JAVA_HOME/bin`. Если jstack вызван без `JAVA_HOME`, на машинах с несколькими JDK будет взят дефолтный `jstack` из PATH (может быть OpenJDK 11, а демон — zulu 25). **В диагностике инфра-сбоя это редко критично** (jstack умеет аттачиться к чужой JVM), но лучше документировать.

### N6. `INFRASTRUCTURE FAILURE` формат ссылается на `(see build skill)`, но в самом отчёте агента нет гиперссылки или ссылки на конкретную секцию
Пользователь, увидевший отчёт в терминале, должен **сам** знать, где скилл. Если он работает в IDE-плагине с ограниченным контекстом — может потеряться. Мелочь, но добавьте полное имя: «see the `Daemon Recovery Procedure` section of the `claude-forge:build` skill».

### N7. `Tools` — `Bash(jps:*)` etc. — но `jps` показывает ВСЕ Java-процессы пользователя, не только Gradle
Если у пользователя одновременно запущены IntelliJ, два демона Gradle разных версий и пара Java-приложений, вывод `jps` будет шумным. Нужен хотя бы `jps -l | grep -i gradle` или `jps -lv | grep -E 'GradleDaemon|KotlinCompileDaemon'` — а это уже `Bash(jps:*)` + фильтрация. Допустимо. **Но**: в Execution Rules это не показано — агент может по неопытности отрапортовать «GradleDaemon PID 12345 (IntelliJ)». Лучше зафиксировать команду.

### N8. `Bash(ps:*)` — слишком широко, не read-only в строгом смысле
`ps` сам по себе read-only, но `Bash(ps:*)` шаблон разрешает **`ps auxf`**, **`ps -ef | grep ...`** — это нормально. **Однако** `Bash(ps:*)` — это pattern-match, и если пользователь переименует `ps` в alias, ломается. **Нормально** для claude-forge.

### N9. CHANGELOG пишет «model haiku → sonnet» как `Changed`, но фактически это breaking change для тех, кто полагался на haiku
Для open-source плагина с пользователями — это breaking. Нужно пометить в `Changed` + дать рекомендацию «fork if you need haiku». **Или** добавить в README «Migrating from haiku». Сейчас CHANGELOG фиксирует смену, README правит заметку — но в тексте «change the frontmatter in a fork if you prefer a different model» — это уже даёт выход, **норм**.

### N10. План не покрывает **сигналы ошибочной классификации** (false positives)
Сценарий: `Timeout waiting to lock` сообщает Owner PID 12345 → агент делает `ps -p 12345` → процесс жив (это `GradleDaemon` от **другого** проекта в параллельной сессии) → агент рекомендует «run daemon recovery procedure first» → главная сессия убивает чужой демон. **Race condition между сессиями**. В отчёте (факт 9) упомянуто: «разные JDK/JAVA_HOME → несколько демонов → increasing memory usage». План это знает, но не учитывает в `ps -p X`: **чей** это демон? Нужна хотя бы `ps -fp X` (покажет cwd), чтобы агент мог добавить в отчёт «owner belongs to <project> — safe to kill» или «owner belongs to unrelated project — escalate to user, do not auto-recover».

### N11. В Acceptance criteria (дизайн) отсутствует пункт про **обновление test/matrix CI**
Сейчас верификация — ручной смоук-тест после мержа. Но если проект в будущем добавит CI, нужно зафиксировать «tests for protocol» (хотя тестов и сборки нет). **Норм**, но стоит добавить в README «Verification» подсекцию.

### N12. `BASH_MAX_OUTPUT_LENGTH` — 30 000 символов, лимит вывода. Для лога Gradle 5 мин это мало
Если сборка падает на середине и лог обрезается — агент видит хвост, не голову. В Execution Rules нет упоминания «читай head/tail/grep при обрезании». **Нужно** дополнить Execution Rules: «if output is truncated, Read the output file with grep/head/tail to find the root cause; do not assume the visible end is the cause».

## Suggestions

### S1. Добавить в README диагностический runbook «If the build is stuck, run:» (3-5 команд) — однострочник для пользователя
Вместо того чтобы пользователь лез в скилл, README может содержать блок:
```
Quick diagnostic:
  jps -lv | grep -E 'GradleDaemon|KotlinCompileDaemon'
  ps -fp <pid>
  jstack <pid> | head -100
```
Это ускорит «что случилось» в первые 60 секунд после жалобы.

### S2. В Execution Rules добавить пункт «if your turn is about to end while a background build is running, write a note to the user — do not stay silent»
Edge case: агент получил bash-вызов, который ушёл в фон, и ход заканчивается. В нынешних правилах «Do not end your turn while the build is still running» — **но что если лимит хода исчерпан?** План этого не покрывает. Предлагаю: если ход заканчивается, агент пишет в ответе «Build X is still running in background (ID Y, output file Z). Re-dispatch build-runner to retrieve final state when complete.»

### S3. В `INFRASTRUCTURE FAILURE` отчёте добавить поле `## Background Task ID` если применимо
Если INFRASTRUCTURE FAILURE возникла **во время** фонового процесса, полезно указать ID задачи, чтобы вызывающий мог напрямую запросить статус. Предлагаю добавить `## Background Task ID (if applicable)` в формат.

### S4. В `Execution Rules` шаг 1 — заменить `timeout: 600000` на `timeout: <по проекту>` с эвристикой
«Always set an explicit timeout» — хорошо, но 600000 (10 мин) для `mvn clean install` мало, для `gradle assembleDebug` — нормально. Лучше: «timeout ≥ 10 min (600000); for full builds with tests consider 30 min (1800000) — must be ≤ BASH_MAX_TIMEOUT_MS». В README уже сказано про BASH_MAX=1800000 — увяжите.

### S5. Команда в `Recommended Action` — `safe to retry` — добавить преамбулу «immediately» vs «after 15–30s»
Сейчас «один повтор сразу» vs «один повтор после паузы» — это уже различимо в скилле, **норм**.

### S6. План мог бы покрыть случай, когда `Recommended Action` — **пустая строка** или **что-то иное**
Что если build-runner вернёт «INFRASTRUCTURE FAILURE» без поля `## Recommended Action`? Скилл не упадёт (Claude Code не валидирует формат), но и не сработает. **Нужна** defensive-логика: «if the format is malformed, treat as BUILD FAILED and report to user». Сейчас — implicit, лучше explicit.

### S7. В CHANGELOG добавить ссылку на отчёт нельзя (untracked), но **можно** в README добавить «See the design rationale in branch history (commit 5bd64a6)».

### S8. `Bash(jstack:*)` — добавить в план пример команды: `jstack <pid> | head -200` (чтобы вывод не превысил 30k)
Если jstack выводит 100k символов — агент увидит обрезанный хвост, не head. **Лучше** зафиксировать `| head -200`.

### S9. `Bash(kill:*)` — дать **главной** сессии, не агенту
В Acceptance criteria дизайна не упомянуто, что main session должна иметь `Bash(kill:*)`. Без этого Daemon Recovery Procedure не сработает. **Нужна** рекомендация в README: «allow `Bash(kill:*)` in main session, or accept the prompt each time».

### S10. Acceptance criteria — добавить пункт про английский язык, дословные строки
Нет автоматизированной проверки. **Лучше** добавить в план grep на кириллицу в agent/skill (её быть не должно).

### S11. После патча, в README обновить блок про `--no-daemon` (сейчас ничего не сказано)
**Можно** добавить в секцию «Notes» однострочник: «The plugin uses Gradle daemons (recommended); do not pass `--no-daemon`».

### S12. В `Build Commands` агента — добавить `--no-daemon` явно запрещённым
Сейчас (план) сказано: «Never add `--no-daemon`» в секции Infrastructure Failures. **Лучше** продублировать в Build Commands.

### S13. Plan не имеет встроенной проверки, что патч **не** сломал существующие секции
Task 1 Step 7 — grep на новое содержание, но **не** на регрессии. Например, `grep -c "BUILD FAILED"` (старый формат) — должны остаться. **Стоит** добавить regression-grep.

### S14. Уточнить, что `model: sonnet` применяется ко всем вызовам build-runner, не только при Gradle
Глобальная смена значит, что Node/Go/Python сборки тоже пойдут на sonnet (дороже). **Стоит** либо (а) обосновать «sonnet нужен всем стекам для стабильного фонового протокола», либо (б) оставить haiku для не-Gradle. **Вариант (а) — проще**.

## Questions

### Q1. Что произойдёт, если **главная сессия** (main) исчерпает лимит на паузе 15–30 с в `Daemon Recovery Procedure` / завершится? План не определяет «куда сохранить состояние восстановления».

### Q2. Почему `Bash(jstack:*)` агенту, а не только главной сессии? Видимо, чтобы агент мог самостоятельно диагностировать «жив ли Owner PID в livelock'е». **Подтвердите логику**.

### Q3. `Recommended Action: safe to retry` — **сразу** или с паузой? Если Owner PID dead, retry сразу безопасен. **Подтвердите**, что семантика «safe to retry» означает «без паузы».

### Q4. Что если `ps -p <X>` показывает, что PID — **зомби** (статус Z)? Зомби уже не держит лок. **Нужна** инструкция: zombie → safe to retry.

### Q5. Проверка «`grep -v "never kill"`» — ненадёжна: вариации регистра/формулировок. **Уточните** pattern.

### Q6. Plan Task 4 Step 2: **Добавьте** проверку `git status --short | wc -l == 1` (только untracked отчёт).

### Q7. **Backward compatibility**: если у пользователя `BASH_DEFAULT_TIMEOUT_MS=60000` — всё равно уйдёт в фон. **Нужна** оговорка в README.

### Q8. Если **пользователь** убивает свою сборку через IDE-кнопку — патч не помогает. Стоит ли в README добавить заметку про cold-start после ручной остановки?

### Q9. Каков SLA на «Background build complete» нотификацию от харнеса? Как ждать технически? Стоит уточнить в Execution Rules.

### Q10. **Гонка при последовательной диспетчеризации**: если предыдущий build-runner **завис** (model error), скилл будет ждать вечно. Нужен таймаут «если build-runner не отчитался за N минут». Вне скоупа плагина, но **стоит задокументировать как ограничение**.
